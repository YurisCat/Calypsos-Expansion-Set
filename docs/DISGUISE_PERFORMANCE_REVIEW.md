# 伪装性能排查记录与后续核查顺序

记录日期：2026-11-16；2026-11-23 补充用户实机反馈。对象为骰子／房规触发的玩家互换外观；怪相雕像仅涉及组合兼容检查。

**0.2.92 已完成首轮优化，待实机。** 2026-11-23 用户先报告伪装激活后换关严重掉帧，随后确认激活即掉帧、解除后恢复。本轮优先减少逐骨骼的 IL2CPP 调用。成品 IL 核对显示，单根已绑定骨骼的旋转赋值从 9 次调用降至 2 次，根旋转相关计算每次同步执行一次。272 项托管外观检查通过，实际帧率待测。用户此前反馈实机拿放物品正常。

若新版仍在换关时恶化，继续查 `DisguiseCurse.ClearRound/ClearViews` 的旧状态释放、`DisguiseHouseRule` 的下一小局重启，以及 `UpdateViews` 在角色／持物变化时的重建。`VisualRigCopy` 使用 `DontDestroyOnLoad`，依赖显式释放。已有三端日志记录了 3 次启动、3 次清除和有限次数的外观创建，未显示逐帧重建，也没有记录每个副本的销毁结果。

三端实测使用带禁用 JIT 优化标志的 0.2.91 DLL。本轮交付启用优化的 Release 0.2.92，实测结果同时反映构建模式和代码改动。若后续需要单独量化代码收益，应使用相同构建模式比较。

## 1. 后续核查顺序

以下是未来重新处理时的顺序，不表示已安排实施，也不表示所有项目都必须修改。

| 顺序 | 项目 | 当前判断 |
| --- | --- | --- |
| 1 | 两阶段整套骨架同步、循环中的重复计算与原生属性访问 | 0.2.92 已减少单次同步的原生调用，两个阶段都保留。先实测新版 |
| 2 | 屏幕外更新、缺少主动视野／距离更新策略 | 存在持续工作；实际蒙皮／剔除成本未测，先确认收益与显示约束 |
| 3 | 显隐、手电挂接与渲染边界恢复 | 存在重复调用；部分承担必要职责，区分无效调用和实际状态变化 |
| 4 | 换关释放及状态变化后的外观重建 | 若仍出现换关恶化或拿放卡顿，再核对释放结果和重建频率 |
| 最后 | 特定时序下可能短暂恢复原身体／昵称 | 只在源码推演及替身时序中复现，用户实机正常；最低优先级，未来优化也可以不处理 |

## 2. 主要性能候选

### 2.1 两阶段整套同步与重复计算

调用链：

- [ExpansionSetDriver](../ExpansionSetDriver.cs) 的 `LateUpdate` 调用 `HeldAppearanceRuntime.RenderAll(disguisesOnly: true)`。
- [HeldAppearanceRuntime](../Visuals/HeldAppearanceRuntime.cs) 的 `BeginContextRendering` 补丁再次调用 `RenderAll()`。
- [PlayerDisguiseAppearance](../Curses/PlayerDisguiseAppearance.cs) 的 `Render` 每次执行 [VisualRigCopy](../Visuals/VisualRigCopy.cs) 的 `SyncPose`，遍历整套 Transform，并同步 renderer 属性与 blend shapes。

这不是复制粘贴了两份相同实现，而是同一更新路径在两个阶段重复执行。每个绑定骨骼还会重复读取副本根旋转、原角色根旋转并求逆；原生属性读写和动画重定向工作随玩家数、骨骼数增加。

**不能把第二阶段整体视为多余。** `LateUpdate` 要在 Unity 准备 renderer 数据前完成手电等挂点；其后原角色的姿态、位置、物品、生命或视角仍可能变化。新增托管检查确认：在两入口之间改变原角色动画及位置，第二入口会刷新副本；跳过它将保留旧姿态。同帧死亡等状态也需要渲染前重新检查及撤销。

若未来优化，优先考察一次同步内部可复用的计算、可减少的原生属性访问及重复设置。保留两个阶段的职责，不直接采用“本帧渲染过就返回”的整体跳过方案，也不承诺可以安全省去一半实际游戏耗时。

### 2.2 屏幕外仍然更新

[VisualRigCopy](../Visuals/VisualRigCopy.cs) 为副本设置 `SkinnedMeshRenderer.updateWhenOffscreen = true`；显示路径没有主动按相机视锥或距离减少 `SyncPose` 调用。原身体启用状态检查不等同于“当前相机看得见”。

可以确认看不见的玩家仍可能产生姿态同步工作，但不能仅据这个开关断言产生了多少 GPU 或蒙皮开销。当前托管测试没有 Unity 的真实剔除、阴影和蒙皮阶段。

若未来处理，须核对重新进入画面、快速转头、旁观／预览视角、多个渲染上下文和阴影需求。不能未经验证直接关闭该开关或按距离停用外观，以免冻结、漏显示或恢复不及时。

### 2.3 显隐、挂接与恢复

[PlayerDisguiseAppearance](../Curses/PlayerDisguiseAppearance.cs) 在渲染结束时恢复原 renderer 并停用副本；下次渲染再同步、启用和隐藏原身。[DisguiseHeldVisuals](../Curses/DisguiseHeldVisuals.cs) 反复将唯一的原版手电网格挂到伪装锚点，并在渲染结束后恢复。

托管计数场景中，每名其他玩家、每个两入口模拟帧有 377 次 `SetActive` 调用，但只有 6 次 `activeSelf` 值改变；6 次 `SetParent` 调用中只有 4 次父节点改变。重复调用不等于同次数的真实启停；根节点启停对子树和 renderer 的引擎维护成本未模拟。

未来可先检查挂点未变时的重复 `SetParent` 等局部工作。正常结束、异常、死亡、外观接管和释放仍必须恢复原网格与姿态，保留原版物品根、碰撞、灯光、开关及其他修改者的所有权。

### 2.4 拿放物品时的缓存重建成本

[DisguiseHeldVisuals.Matches](../Curses/DisguiseHeldVisuals.cs) 检查当前手持物、手电及其 renderer。失配会使整个 [PlayerDisguiseAppearance](../Curses/PlayerDisguiseAppearance.cs) 无效，随后由 [DisguiseCurse.UpdateViews](../Curses/DisguiseCurse.cs) 重新建立身体、骨骼绑定及持物缓存。

这可能产生拿放瞬间的资源创建与扫描成本；稳定持有时会复用已有显示，不是持续逐帧销毁重建。重建显示不重新随机分配身份。

若日后实际测到频繁拿放卡顿，可评估单独刷新持物缓存，让未变的身体和昵称继续复用。该方向需要验证转交、尸体、手电替换、原版角色更换及失败回滚；当前不实施，也不将其直接当作持续掉帧根因。

## 3. 已完成的本地验证及证据边界

### 3.1 托管耗时对照

当前生产显示代码与 Unity 替身运行于 Release/net6.0/x64。按历史日志中 183 Transform／8 renderer 的数量构造合成角色；数量有历史依据，解剖层级和 renderer 布局仍为合成模型。每场景预热后交替运行一次／两次入口，共 48,000 个计时模拟帧。

下表为批次平均帧耗时的中位数，单位是毫秒／模拟帧，不是实际游戏耗时或逐帧 P95。

| 显示其他玩家数 | 一次入口 | 当前两次入口 | 第二次增加 |
| --- | ---: | ---: | ---: |
| 1 | 0.040 | 0.082 | 0.042 |
| 3 | 0.116 | 0.236 | 0.120 |
| 7 | 0.273 | 0.555 | 0.283 |

对照中的工作量约翻倍，绝对耗时较小且随人数近似线性增加。一次入口只是量化第二次调用的对照，不是已验证正确的优化方案。

未测 IL2CPP 跨界调用、真实 Transform／renderer／层级维护、蒙皮、剔除、阴影和 GPU，也未测整个插件 Tick。因此不能用这些数字证明或排除明显掉帧、换算 FPS，或承诺未来优化收益。替身预热后当前线程零分配也不能推导真实 interop 或引擎零 GC。

### 3.2 功能与生命周期检查

六组托管检查完成：配对／协议 52,773 项、抵达表现 26 项、图标 24 项、房规 136 项、骰子接入 122 项、外观 272 项。外观包含 44 项新增阶段、组合和时序特征检查；断言数量包含循环与模糊变异，不等于同等数量的真实游戏场景。时序特征检查通过表示复现了代码行为，不表示该行为被认可或实机已出现。

原始方法、生产文件哈希及运行输出保留在本机忽略的验证目录中。验证概述与历史证据见 [DEVELOPMENT](../DEVELOPMENT.md#2026-11-16伪装持续开销的源码检查与托管对照)。本轮没有新增游戏或真实联机性能验收。

## 4. 未来优化必须保留的功能

| 范围 | 必须保留的行为 |
| --- | --- |
| 配对与快照 | 角色、衣色、头饰和昵称按既定快照显示；拿放、掉落、死亡不重新随机配对；角色更换按现有规则刷新 |
| 死亡／复活 | 死亡时释放外观、恢复原身体／昵称；配对继续保留，复活后恢复原配对伪装；他人的死亡不擅自重抽 |
| 拾取／放下尸体 | 两种尸体结构均排除外来骨架和 renderer，不复制、不换材质、不随搬运者变形；搬运者的配对不变 |
| 第一人称与手持 | 本人普通第一人称保留原样；第三人称挂点、持物偏移及原版动作／物理／灯光保持 |
| 手电 | 保持唯一原版网格，安全结构才临时挂接；不支持时保留原位置；退出正确恢复，不覆盖其他所有者 |
| 视觉组合 | 宽体／大头继续作用于伪装外观；怪相优先，释放后恢复当前伪装；快速切换不残留 |
| 骰子／房规 | 保留资格、过滤与原版回合流程；重复施加不重配；规则小局重配及撤销的状态归属保持 |
| 联机恢复 | 保留兼容、认证、Ready、真实实体绑定及协议校验；晚加入、重连、换角色和快照超时按现有契约恢复 |
| 图标／提示／特效 | 死亡不解除有效状态图标；一次性表现与可恢复状态分离，晚加入和复活不补播历史事件 |
| 清理与失败 | 解除、换局、断线、销毁和异常均撤销自身修改、释放资源，不覆盖原版或其他 MOD 的状态 |

当前组合检查中，怪相优先级使用调度替身并结合实际怪相源码追踪；真实怪物模型、动画、相机及网络执行没有由本轮替身证明。未来如果修改，仍需按影响范围做针对性游戏验证。

## 5. 后续处理方式

先实测 0.2.92，关注伪装激活、换关和解除时的画面与帧率。若明显掉帧仍在，再按下述方案采集现场指标。

后续按以下方案围绕已报告的换关条件验证。方案尚未实现为诊断代码，也没有据此生成或部署新 DLL。

### 5.1 先做同条件实机对照

保持游戏／MOD 版本、人数、多开数量、画质、后台运行和锁帧设置一致，在可比的地图、位置与视角记录整帧耗时；主机与各客户端分别记录。

| 场景 | 要回答的问题 |
| --- | --- |
| 未启用伪装，正常进入下一关 | 换关本身和多开负担是否已经造成同等下降 |
| 启用伪装，留在当前关卡 | 不换关时是否也持续变慢 |
| 启用伪装，再进入下一关 | 对齐已报告的触发条件，记录下降开始于清理、生成还是进入后 |
| 掉帧后解除伪装 | 帧耗时是否随有效伪装显示／更新停止而恢复；该结果只能缩小范围，不能单独证明根因 |
| 连续再换两关，或离房重建 | 是否逐关累积，以及会话重置后是否恢复 |

先确认来源：骰子伪装应在原版小局清理边界解除；大师规则在该边界清理本小局显示后，下一小局按规则重新分配。规则模式下不能简单以“换关后还有外观”认定残留。

### 5.2 诊断版只测必要指标

诊断应由 DebugMode 控制，在激活、清理入口、规则重新启动、外观创建／释放及换关前后记录状态。稳定运行时每两秒汇总，避免逐帧格式化和刷日志；稳定身份、资源、配置与协议保持。

- 记录 `ClearRound` 是否实际执行、服务器／客户端有效伪装状态、规则归属和快照修订，检查实际原生换关调用是否经过当前补丁。
- 记录视觉副本创建、释放与存活数量，按玩家和用途区分基础伪装、持物及视觉组合；允许正常的隐藏基础副本与当前高优先级外观共存，不能只用玩家数粗略判断重复。Unity Destroy 延迟至帧末，须过该边界后核对销毁结果。
- 为 `Matches` 失配记录原因：角色实体、rig、body renderer、持物、手电、视角或配对变化。状态稳定后仍不断创建／释放，才支持“持续重建”的判断。
- 汇总每帧渲染入口次数、姿态同步次数／节点数、创建／重建耗时及刷新耗时。计时放在阶段边界，不能逐骨骼增加诊断成本，也不能把一次性初始化混成持续刷新。
- 同时保留整帧耗时。模块托管耗时低但整帧很慢时，继续核对原生层级／renderer、屏幕外蒙皮及 GPU 开销；源码计数不能直接代替这些数据。

### 5.3 按证据选择修改点

| 诊断结果 | 对应修改方向 |
| --- | --- |
| 原生小局清理未经过当前入口 | 在核对过的实际调用边界补齐幂等清理，区分骰子解除与规则重启；不能只靠场景加载回调清空所有配对 |
| 应释放的旧副本过帧末仍存活或持续更新 | 修正所有权与释放路径，先恢复原身／持物／手电，再销毁自有副本并移出更新集合；同时覆盖持有视觉组合 |
| 同一稳定玩家不断失配和重建 | 修正具体失配原因或刷新粒度，优先复用未变化的身体；不要每次持物变化都重建整套外观 |
| 副本数量稳定，刷新阶段本身耗时高 | 缓存单次同步的不变计算，减少重复原生属性访问与挂接；保留渲染前状态复核及必要的姿态刷新 |
| 托管阶段正常，原生／渲染成本异常 | 再针对显隐、屏幕外更新、剔除和阴影做独立对照；不直接批量关闭 renderer 或删第二入口 |

每次围绕一个已测出的原因修改，重复同一换关路径验证帧耗时和资源数量。旧版／新版对照须使用同样的游戏和 MOD 组合，避免同时修改画质、人数或其他插件。

### 5.4 修复验收范围

除了激活后换关不再触发异常下降，还须覆盖骰子／规则的不同寿命、连续换关、解除／重开、死亡复活、搬运及放下尸体、普通持物／手电、宽体／大头／怪相切换，以及主机／客户端、晚加入和断线清理。托管检查可验证计数、幂等和恢复逻辑，真实掉帧是否消失仍由游戏对照确认。特定时序的短暂原貌窗口继续按下一节最低优先级处理。

## 6. 最低优先级：特定时序的短暂原貌窗口

源码和替身可构造以下顺序：插件已更新显示缓存，随后手持物改变，渲染检查释放旧外观，下一次 Update 才重建。这段期间可能短暂显示原身体和昵称；尸体外观和保存的配对不变。

**用户已明确反馈实机拿放物品正常。** 目前没有证据证明原版实际执行顺序触发了上述窗口，也没有实际画面证明可见闪回。不能将它写成已确认的实机故障，更不能用它解释持续掉帧。

该项排在所有性能候选之后；未来即使进行性能优化，也可以保持现状、不修改这条路径。仅在出现明确实机复现，或其他必要修改触及这里且能低风险处理时，再评估是否改动。
